# 夜间 MR 评审提示词

你正在一个 Java / Spring Cloud 多模块仓库中做代码评审。仓库根目录就是当前工作目录。

请评审 **MR #{{IID}}** 的改动，基线分支是 `origin/{{BASE}}`。

## 第一步（必须执行）

```
git diff --stat origin/{{BASE}}...refs/ai/mr-{{IID}}
```

## 第二步

对每个改动文件，读它的**完整上下文**，不要只看 diff 片段。
需要了解被调用的类时，继续往下读。只读，不要修改任何文件。

## 检查清单

按顺序看，发现问题才写，没问题不要硬凑。**不要臆测业务规则**——你判断不了业务对错，
只评审代码层面。

1. **正确性**：空指针、集合越界、并发、事务边界（`@Transactional` 的位置/传播行为/是否自调用失效）、
   幂等（重试会不会重复扣款/重复入账）
2. **本仓库铁律**（见根目录 `AGENTS.md`）：
   - 返回体是否用了 `Result`，有没有冒出 `ResponseEntity`
   - 当前用户是否走 `UserHolder`，有没有在方法签名里传 `userId`
   - 有没有新建 `XxxUtil` / `XxxHelper`，而 `docs/UTILITIES.md` 里其实已有等价实现
3. **风险**：SQL 注入、越权（有没有校验数据归属）、日志里打印敏感信息、
   金额精度（`BigDecimal` 的 `equals` / `scale` / 除法舍入）
4. **可测性**：有没有配套测试；如果没有，指出**最应该补的那一个**用例

## 输出格式（严格遵守）

```
## 结论
通过 / 需修改 / 有阻塞问题（一句话说明）

## 必须改（会阻塞合并）
- `文件:行` —— 问题 —— 建议怎么改

## 建议改（不阻塞）
- `文件:行` —— 问题 —— 建议

## 我检查过、确认没问题的点
- （列 2~4 条，让评审者知道你的覆盖面）

## 我不确定的地方
- （需要人判断的业务逻辑、外部约定、你没读到的调用方）
```

「我不确定的地方」这一节很重要，**不要跳过**。宁可承认没把握，也不要编一个看起来
很像的理由——那比漏报更浪费时间。
